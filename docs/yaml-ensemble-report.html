Itzï · branch comparison: ensemble vs main

YAML configuration & ensemble runs

One YAML document now describes a study rather than just one run. Lists of inputs or settings turn it into several simulations, which Itzï checks and runs one at a time.

What changed

Before

Each INI file described one simulation. A batch ran several INI files, with the legacy hotstart and resume workflow.

On this branch

.yaml files contain one or more documents separated by ---. Each document defines an ensemble: a shared domain and clock, plus one or more combinations of input maps and numerical parameters. A command can process several YAML files and legacy INI files in order.

The .yaml suffix selects YAML parsing. Other suffixes use the deprecated INI reader; invalid YAML is never silently treated as INI.

A four-member study

This example assumes the GRASS session can see the named rasters. Save it as study.yaml:

schema_version: 1
ensemble:
  id: "study"
domain: {}
time:
  duration: "02:00:00"
  record_step: "00:05:00"
input:
  ground_elevation: "terrain"
  friction: "manning"
  rainfall_rate: ["rain_10yr", "rain_100yr"]
parameters:
  cfl: [0.5, 0.7]
outputs:
  rasters:
    prefix: "study_{simulation}"
    variables: [water_depth, flow_speed]
  statistics:
    file: "results/{simulation}.csv"

Two rainfall choices × two cfl choices = four simulations. Each has the same terrain, friction, region, duration and recording interval. variables chooses what to save; it does not multiply the number of simulations.

YAML fieldPlain-English meaning
schema_version, ensembleFormat version 1 and a unique study ID. An optional name is descriptive.
domainOne GRASS context for the ensemble. Leave grass out to use the active session; optionally specify grass.database, project, mapset together, and executable. An optional region and mask apply to all members.
timeOne clock for every member: duration alone, start + duration, or start + end, always with record_step. Durations are positive HH:MM:SS, including hours over 23.
inputTerrain (ground_elevation) and friction are required. Other raster/space-time raster inputs are optional. A scalar fixes a value; a nonempty list sweeps it.
parameters, drainageNumerical settings use core defaults unless supplied; drainage is optional and requires the SWMM input and three exchange coefficients. Their lists can also be swept.
outputsOptional raster, CSV statistics, drainage-vector and manifest destinations. The section itself is required, even if empty (outputs: {}).

input.infiltration is either {type: "none"} (the default), {type: "constant", rate: "map"}, or type: "green-ampt" with maps for effective porosity, capillary pressure and hydraulic conductivity (optionally soil water content). A list of complete infiltration alternatives counts as one sweep dimension.

From choices to runnable members

  1. Read and expand. YAML is safely parsed, checked against a strict versioned schema, and every combination of list values is produced. Unknown fields, duplicate or merge keys, custom tags, empty documents and duplicate sweep values are rejected. An explicitly separated later document can still load after an earlier document fails.
  2. Resolve against GRASS. A fresh process opens the requested or active GRASS context, finds the region and mask, resolves each input as a raster or space-time raster dataset, and builds a simulation configuration. Ambiguous or missing inputs fail for that member. Optional SWMM files are resolved relative to the YAML file.
  3. Name and check outputs. Each successfully resolved member gets a sim-xxxxxxxx ID from a digest of its normalized domain, time, inputs, settings, mask and drainage information. This ID is based on the resolved run, not its position in the sweep. Itzï renders output templates, then checks for duplicate IDs, collisions between members, and output names that would overwrite inputs or the mask.
  4. Validate run requirements and run. Selected members are checked for usable input data, temporal coverage, existing destinations and a still-matching GRASS environment. The real run writes a manifest, then runs eligible members sequentially in separate processes. After the first member, each next member's run requirements are validated again because earlier output may have changed what exists.

The limits apply before member selection: at most 100 candidate simulations per document and 200 across the batch.

The INI path runs each file in a separate subprocess and supports mapped --resume-from checkpoints. The YAML real-run loop repeats the per-member run-requirements validation and execution boxes for each selected, eligible member. Each worker opens a GRASS session with GrassSessionManager.open(); separate processes prevent GRASS temporal state leaking across mapsets.

Using and reading the results

itzi run study.yaml --dry-run
itzi run study.yaml --member 'study#sim-xxxxxxxx'
itzi run study.yaml

First inspect the dry-run output for the actual sim-… ID; replace xxxxxxxx above with those eight hex digits. Repeat --member to choose several. If the command contains exactly one ensemble, the simulation ID may be unqualified. -o permits overwriting existing destinations.

  • Raster variables become GRASS space-time raster outputs named from the prefix plus _variable; each record has its own map. Statistics go to CSV, and optional SWMM drainage results can go to a space-time vector dataset.
  • {ensemble} and {simulation} are the only template placeholders. The manifest path may use {ensemble}, but not {simulation}. Filesystem paths in YAML are relative to its file; output GRASS map names must be unqualified names in the execution mapset.
  • A real run writes results/study.manifest.yaml beside this example file by default. outputs.manifest.file overrides that path. The YAML manifest records source digests, member choices, destinations, statuses (planned, running, completed, validation_failed, execution_failed, not_selected) and failures/elapsed time when applicable.
  • Dry runs perform validation without creating manifests or model outputs. Document and member failures are reported; valid members in other documents can still be processed. The command ends with an error status when relevant validation or execution fails.

Compatibility: A plain INI-only run keeps its old execution and hotstart-resume path. INI files in the new batch planner (for example, mixed with YAML or using --dry-run) are adapted as single-member ensembles. YAML resume and checkpoint creation are not yet supported; --resume-from cannot be combined with the new ensemble path.
